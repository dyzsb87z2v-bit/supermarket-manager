# مدیریت سوپرمارکت (نسخهٔ ۰.۱)

یک وب‌اپ ساده برای مدیریت موجودی، فروش، سفارش و گزارش یک سوپرمارکت کوچک. **صفر هزینه، صفر وابستگی** (فقط HTML/CSS/JavaScript)، مناسب موبایل، قابل نصب روی صفحهٔ اصلی گوشی (PWA) و **کار آفلاین**.

### محدودیت‌ها و قواعد رعایت‌شده
- **داده‌های نمونه** ساختگی‌اند (بارکد از محدودهٔ داخلی EAN 200–299، تأمین‌کنندگان خیالی) و در یک فضای کاملاً جدا («نمونه») نگه‌داری می‌شوند. کد اجازه نمی‌دهد نمونه در «واقعی» نوشته شود یا پشتیبان نمونه در واقعی بازگردانی شود (تست شده).
- **اطلاعات مشتری** هیچ‌جا جمع نمی‌شود؛ فیلدی برای آن وجود ندارد.
- **سفارش خودکار وجود ندارد.** فقط متن آلمانیِ پیشنهادی ساخته می‌شود که خودتان کپی و ارسال می‌کنید.
- هیچ سرویس خارجی، API، CDN یا فونت اینترنتی استفاده نشده؛ همهٔ فایل‌ها از خود برنامه لود می‌شوند.
- قیمت‌ها با عدد صحیح سنت ذخیره می‌شوند. مالیات (۷٪/۱۹٪) در محاسبات **در نظر گرفته نشده**؛ «سود خام» = فروش − بهای خرید ثبت‌شده.
- پیش‌بینی ساده است: روزهایی که کالا تمام شده بوده در میانگین جبران نمی‌شود (تقاضای کالاهای پرتمام‌شونده کمتر از واقع برآورد می‌شود). هیچ مدل فصلی/تعطیلات ندارد.
- تاریخ انقضای هر محموله از «ورود کالا» می‌آید؛ اگر موقع ورود وارد نشود، هشداری نمی‌دهد.

## زبان‌ها (چندزبانه‌سازی)
- زبان از تنظیمات مرورگر انتخاب می‌شود (ترکی ← ترکی، آلمانی یا هر چیز دیگر ← آلمانی). از منوی بالای صفحه یا «تنظیمات» عوض می‌شود و ماندگار است. عدد، پول و تاریخ طبق زبان قالب‌بندی می‌شوند (مثلاً `32,3 %`).
- **متن سفارش برای تأمین‌کننده** جداگانه به آلمانی یا ترکی ساخته می‌شود (تنظیمات ← زبان متن سفارش).
- همهٔ زبان‌ها فقط در `src/core/locales.js` ثبت می‌شوند. برای افزودن زبان: یک فایل در `src/ui/i18n/` و یک سطر در آن رجیستری؛ تست‌ها خودشان کامل‌بودن را وارسی می‌کنند.
- **گِیت ترجمه (در `npm test`)** شکست می‌خورد اگر: کلیدی در یک زبان کم یا اضافه باشد، متن خالی باشد، `{متغیر}` ناهماهنگ باشد، حالت جمع (one/other) کم باشد، متن ترجمه‌نشده کپی شده باشد، خط نوشتاری اشتباه باشد (مثلاً لاتین در فارسی)، کلید بدون استفاده یا بدون تعریف باشد، یا متن خام داخل کد صفحه‌ها باشد. خودِ گِیت هم با بسته‌های عمداً خراب تست شده است.
- **تست مرورگری** با «زبان شبه‌ساختگی» (`?lang=en-XA` فقط روی localhost) همهٔ صفحه‌ها را می‌گردد: هر متنی که از بستهٔ زبان نیامده باشد یا هر جا که با ۳۵٪ متن بلندتر از عرض صفحه بیرون بزند، تست را شکست می‌دهد.
- ⚠️ **ترجمه‌های آلمانی و ترکی را من نوشته‌ام و هنوز هیچ فردِ بومی‌زبان آن‌ها را بازبینی نکرده است** (در رجیستری وضعیت `beta` و `reviewedBy: null`). قبل از استفادهٔ تجاری یک آلمانی‌زبان و یک ترک‌زبان متن‌ها را بخوانند.

## صندوق: چه چیزی واقعاً ممکن است
- **لحظه‌به‌لحظه** فقط وقتی ممکن است که خودِ صندوق هر فروش را بفرستد (API/Webhook) و یک سرور مشترک آنلاین داشته باشیم. بدون دانستن مدل صندوق، این قابل طراحی نیست و **ساخته نشده**.
- **راه مستقل از برند:** صندوق‌های دارای TSE در آلمان باید خروجی استاندارد «DSFinV-K» بدهند (طبق BZSt ساختار فایل‌ها و فیلدها برای همهٔ سیستم‌ها یکسان است). برنامه فایل `lines.csv` (یا کل ZIP) را می‌خواند: *تنظیمات ← ورود از صندوق*. این یعنی «پس از هر بستن روز» نه لحظه‌ای.
- قواعد: فقط ردیف‌های `GV_TYP = Umsatz` (فروش) حساب می‌شوند (پانت، تخفیف، بن‌هدیه رد می‌شوند)؛ ردیف‌های `P_STORNO = 1` رد می‌شوند؛ برگشت کالا (MENGE منفی) با فروش همان روز جمع می‌شود؛ تطبیق کالا با `GTIN` (یا `ART_NR`) = بارکد کالا؛ واحد نامطابق (مثلاً گرم در برابر کیلو) رد می‌شود و تبدیل نمی‌شود؛ هر کاس‌شلوس (`Z_KASSE_ID`+`Z_NR`) فقط یک‌بار ثبت می‌شود؛ ورود «همه‌یا‌هیچ» است.
- ⚠️ **با خروجی هیچ صندوق واقعی آزمایش نشده** (فقط با فایل‌های ساخته‌شده از روی مشخصات DSFinV-K ۲٫۳). جداکننده و encoding از روی خود فایل تشخیص داده می‌شود ولی در منبع رسمی که خواندم تأیید نشد. لغو کامل یک بن که فقط در `transactions.csv` (`BON_STORNO`) علامت می‌خورد خوانده نمی‌شود. تاریخ فروش = تاریخ `Z_ERSTELLUNG`؛ اگر صندوق بعد از نیمه‌شب بسته شود، فروش به روز بعد می‌افتد.

## فرمول پیشنهاد سفارش
```
میانگین روزانه = فروش N روز اخیر ÷ تعداد روزهای تاریخچه   (N پیش‌فرض ۲۸؛ حداقل ۷ روز مبنا)
نقطهٔ سفارش    = میانگین × زمان‌تحویل + حداقل‌موجودی
هدف            = میانگین × (زمان‌تحویل + روزهای پوشش) + حداقل‌موجودی      (پوشش پیش‌فرض ۷ روز)
اگر موجودی ≤ نقطهٔ سفارش:  مقدار = هدف − موجودی، گردشده به بالا تا مضرب «اندازهٔ بسته»
```

## اجرا

**برای استفادهٔ واقعی روی موبایل** فایل‌ها باید روی یک آدرس HTTPS قرار بگیرند (برای نصب PWA و کار آفلاین لازم است). هاست‌های استاتیک رایگان مثل GitHub Pages (فقط مخزن عمومی)، Cloudflare Pages یا Netlify کار می‌کنند، فقط پوشهٔ `supermarket-manager` را منتشر کنید. **من هیچ‌کدام را راه‌اندازی یا آزمایش نکرده‌ام.** نکته: داده‌ها فقط داخل مرورگرِ همان گوشی می‌ماند، پس از آدرس عمومی بودن اپ نگران افشای داده نباشید؛ ولی مرتب «پشتیبان» بگیرید.

📄 راهنمای قدم‌به‌قدم انتشار از روی موبایل: [`DEPLOY.md`](DEPLOY.md)

**روی کامپیوتر برای آزمایش:**
```bash
cd supermarket-manager
python3 -m http.server 8080        # سپس http://localhost:8080 را باز کنید
```

**تست‌ها:**
```bash
npm test                           # ۳۶ تست منطق (Node ≥ 20، بدون نصب پکیج)
node tests/e2e-smoke.cjs           # اختیاری: تست مرورگری (نیاز به Playwright)
```

## ستون‌های CSV
- **کالاها:** `barcode; name_de; name_tr; category; supplier; buy_price; sell_price; unit; min_stock; pack_size; active; stock; expiry` (نام ستون به آلمانی/ترکی هم پذیرفته می‌شود: Artikel، EK، VK، Mindestbestand، Barkod …). ورود مجدد بر اساس بارکد «به‌روزرسانی» می‌کند. ستون `stock` «موجودی شمارش‌شده» است: فقط اختلاف با موجودی فعلی ثبت می‌شود، پس ورود دوبارهٔ همان فایل چیزی را تغییر نمی‌دهد. ستون‌های `sku`، `sold14`، `lead` و `targetDays` (از نسخهٔ قدیمی تک‌فایلی) نادیده گرفته می‌شوند؛ `pack` همان اندازهٔ بسته است.
- **فروش / ورود کالا:** `date; barcode; qty` و اختیاری: `unit_price; unit_cost; expiry; type; branch; note`. تاریخ `2026-03-31` یا `31.03.2026`.
